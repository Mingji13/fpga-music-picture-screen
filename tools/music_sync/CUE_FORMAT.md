# MCUE v1：音乐画屏切图点文件

这是本工程自定义的二进制格式，与音频软件常见的文本 `.cue` 分轨表不同。
PC 导出器和 FPGA RTL 读取已实现；需使用支持 CUE 的新位流。
本轮构建、时序和板测状态见 [CUE 接入记录](../../board_tests/cue_clean_20261028/RESULT.md)。

## 文件配对与时间基准

SD 卡根目录以同编号配对：`SONG1.PCM` / `SONG1.CUE`，直到 `SONG16`。
PCM 格式固定为 48000 Hz、单声道、16 位有符号小端、无文件头。
文件长度必须是偶数字节，样本数等于 PCM 字节数除以 2。

切图位置使用从零开始的 PCM 样本序号，而不是秒数或 SD 读取进度。
位置 `n` 表示音频即将播放第 `n` 个文件样本时申请开始转场，此前已播放 `n` 个样本。
例如 `274176` 对应 `274176 / 48000 = 5.712` 秒；位置 0 对应首个文件样本。
这里指开始转场；实际画面仍受帧边界、转场过程和显示设备延迟影响。

启动等待期间、暂停期间、FIFO 空而补零时，都不能推进文件样本计数。
PCM 文件里本身的静音仍属于有效样本，必须照常计数。
切歌或重新播放一首歌曲时，从该曲第 0 个文件样本和第一条 CUE 重新开始。

## 字节布局

所有整数均为无符号、小端；SHA256 保持摘要的原始 32 字节顺序。
文件由 64 字节头和紧随其后的样本位置数组构成，无尾部填充。

| 字节偏移 | 长度 | 字段 | v1 取值/含义 |
| --- | --- | --- | --- |
| 0 | 4 | magic | ASCII `MCUE` |
| 4 | 2 | version | 1 |
| 6 | 2 | header_bytes | 64 |
| 8 | 4 | sample_rate | 48000 |
| 12 | 4 | sample_count | PCM 文件样本数，1～4294967295 |
| 16 | 4 | cue_count | 切图点数量，1～1024 |
| 20 | 4 | flags | 必须为 1：位置表示申请开始转场 |
| 24 | 32 | pcm_sha256 | 对应完整 PCM 文件的 SHA256 摘要 |
| 56 | 4 | checksum | 整个文件的 32 位加法校验补数 |
| 60 | 4 | reserved | 0 |
| 64 | cue_count × 4 | positions | 严格递增的样本序号数组 |

每个位置满足 `0 <= position < sample_count`，不允许重复。
文件长度必须恰好为 `64 + 4 * cue_count` 字节。
一首曲子最多 1024 个点，RTL 仿真已覆盖满容量表。
点表最多 4096 字节，加头共 4160 字节。FPGA 在每首曲子播放前复用音频文件读取器，
将当前曲的点表加载到双时钟 BRAM；不同时保存全部 16 首歌曲的点表。

校验方法：把整个文件按连续的小端 32 位字相加，对 `2^32` 取模，结果必须为 0。
生成时先将偏移 56 的字段置 0，算出总和，再写入该总和的二进制补数。
这只检查常见传输/内容损坏，不是密码学完整性证明，也不保证发现所有修改。

## PC 校验与 FPGA 接收行为

导出器要求 JSON 已标记 `reviewed=true`，并重算 PCM 的 SHA256 和样本数，
核对 JSON 中的拍点、参数和最终切图点一致后才输出。已有文件不覆盖。
`inspect-cue --pcm` 同时检查二进制格式、校验和、位置范围及 PCM 哈希。

SHA256 用于 PC 配对校验；保留摘要不要求 FPGA 实现 SHA256 运算电路。
FPGA 检查头字段、实际文件长度、PCM 样本数、点表范围/顺序和加法校验，整表通过后才启用。
只检查长度无法识别被替换成另一首、但长度恰好相同的 PCM；应将 PC 核验后的同编号两文件配套复制。

播放策略：

- 仅 WAV 模式且自动轮播开启时使用有效点表；缺表或表无效时保留原定时轮播。
- 曲中开启自动轮播时，跳过过去的点，只等未来的点。
- 转场正忙或下一图尚未准备好时，跳过当前点，不在稍后补切而打乱节拍。
- 点表校验应在启用该表前完成；不能先按未验证的数据切图再检查。

以上行为已通过 RTL 仿真，实际音乐与转场的听感仍需上板确认。
